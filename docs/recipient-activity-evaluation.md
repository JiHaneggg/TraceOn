# 수취 계좌의 평소 입금과 최근 입금 비교 · 2026-11-23

같은 수취 계좌의 평소 송금 계좌 수와 최근 수를 비교했다. 새 평가 표본에서 **최근 송금 계좌 2개 이상이면서 평소보다 1개 이상 증가** 조건은 최근 24시간의 계좌 수만 검사할 때 잡았던 세탁 80건을 모두 유지하면서 정상 오탐을 77건에서 63건으로 줄였다.

## 계산 방법

- 대상 시각 기준 최근 24시간과 바로 앞의 24시간 구간 5개를 사용한다. 각 구간의 고유 송금 계좌 수와 입금 건수를 센다. 평소 값은 과거 5구간의 중앙값이다.
- 기존 그래프의 계좌당 50거래 상한을 적용하지 않는 원본 SQLite 인덱스에서 수취 계좌·시간을 조건으로 읽는다. 동일 송금 계좌의 여러 입금은 송금 계좌 수에는 한 번만 들어간다.
- 대상 거래는 최근 구간에 한 번 넣는다. 그 시각의 다른 거래는 원천 시각에서 순서를 확정하기 어려워 제외한다. 미래 거래와 자기 계좌 이체도 제외한다.
- 원본 시작 시각 때문에 과거 5일과 최근 1일이 모두 확보되지 않거나, 과거 5일 중 실제 입금이 있는 날이 3일 미만이면 비교 불가로 기록한다. 한 계좌의 범위 내 입금이 50,000건을 넘을 때도 비율 계산을 보류한다.
- 비교 불가 사례에서는 기존 집금 룰의 경고를 유지한다. 이번 실험은 기존 연구 후보의 집금 결과에 조건을 추가하며, 순환·분산 경고는 동일하게 반영한다.

구현은 `data-pipeline/recipient_activity.py`에 있다. 비교 가능한 거래는 `typicalSenderCount`, `recentSenderCount`, `senderDelta`, `senderRatio`와 입금 건수의 대응 값을 제공한다. 조회 기간과 과거 일별 집계도 제공한다. 평소 2개 계좌에서 입금되던 곳에 최근 5개 계좌에서 입금됐다면 증가량은 3개, 평소 대비 2.5배다.

## 평가 결과

이전에 사용한 검증 250건에서 송금 계좌 수·입금 건수의 비율과 증가량을 조합한 30개 조건을 비교했다. 보정 Recall 90%와 오탐 감소를 함께 달성한 조건은 없었다. 검증 오탐률 상한 50%에서 Recall이 가장 높은 비교 조건과 실제 증가가 필요한 조건을 고정했다. 평소 수치를 쓰지 않고 최근 24시간의 송금 계좌 수만 보는 비교군도 포함했다. 세 조건 모두 같은 사례에서 이력 부족 시 기존 집금 경고를 유지했다.

새 표본은 V2 검증 구간 이후에서 뽑았고, 시연 자료 및 기존 V2 검증·최종평가와 거래 ID·알려진 패턴 묶음이 겹치지 않도록 했다. 정상 150건과 세탁 100건을 같은 기준으로 대조했다.

| 새 평가 표본의 조건 | 세탁 탐지 / 100 | 정상 오탐 / 150 | 보정 Recall | 오탐률 |
|---|---:|---:|---:|---:|
| V2 집금 연구 후보 | 84 | 104 | 83.87% | 69.33% |
| 최근 24시간에 송금 계좌 2개 이상 | 80 | 77 | 79.72% | 51.33% |
| 최근 송금 계좌 2개 이상이며 평소와 같거나 많음 | 80 | 76 | 79.72% | 50.67% |
| 최근 송금 계좌 2개 이상이며 평소보다 1개 이상 많음 | 80 | 63 | 79.72% | 42.00% |

실제 증가 조건은 V2 연구 후보와 비교해 오탐을 41건 줄이는 대신 세탁 거래 4건을 더 놓쳤다. 단순 24시간 조건과 비교하면 같은 세탁 80건을 잡고 오탐을 14건 더 줄였다. 기존 검증 표본에서의 실제 증가 조건은 보정 Recall 87.80%, 오탐률 42.00%였다. V2의 Recall 90% 목표에 아직 미달하므로, 평소 대비 증가량은 결합 모델의 비교 특성으로 사용하고 정해진 기준의 자동 경고 적용은 추가 평가를 거친다.

새 표본에서 비교 가능한 이력이 있었던 거래는 **171/250건**이다. 정상은 127/150건, 세탁은 44/100건이다. 특히 세탁 표본의 56건에서 평소 이력이 부족했다. 원본 전체가 약 18일치인 만큼 여러 주에 걸친 요일 효과는 검증 범위 밖이다. 새 표본도 같은 합성 데이터셋에서 뽑았으며, 기간 내 수취 계좌와 거래 이력은 서로 겹칠 수 있다. 결과 해석은 동일 표본의 조건별 차이와 이력 확보율을 함께 본다.

## 재현

V2 평가 자료·고정 설정과 HI-Small 원본 인덱스를 준비하고 저장소 루트에서 실행한다. 새 결과 파일명으로 실행하면 기존 측정값이 보존된다. 기존 V2 최종평가 파일은 새 표본에서 대상과 패턴 묶음을 제외하는 용도로 사용한다.

```powershell
python scripts/evaluate-recipient-activity.py develop --output artifacts/recipient-activity-frozen-next.json
python scripts/evaluate-recipient-activity.py evaluate --freeze artifacts/recipient-activity-frozen-next.json --output artifacts/recipient-activity-fresh-next.json
```

이번 기록은 `artifacts/recipient-activity-frozen-20261123-final.json`과 `artifacts/recipient-activity-fresh-20261123.json`에 있다. 소스 인덱스의 독립 SQL 집계로 새 평가 250건의 1,500개 구간에서 고유 송금 계좌 수와 입금 건수를 대조했다. 데이터 검사 34개도 통과했다. 연결 코드·집계 문서는 공유할 수 있으며 평가 산출물은 Git에서 제외한다.
