- `data-pipeline/tests/test_graph_diagnostics.py`: 합성 자료로 미래 거래·허위 노드·금액 변조·중복·상한·선언하지 않은 생략·실행 예산·쓰기 거부 등15개 검사.

조회 조건은 `(1홉, 이전1일)`, `(2홉, 이전7일)`, `(3홉, 이전7일)`이다. 계좌별50건·전체1,000건의 기존 상한을 유지한다. 시작/종료 적재 자료의 지문이 바뀌면 실행을 실패 처리한다. 고정 읽기 템플릿 외의 쿼리와 임의 PROFILE은 거부하고 개별 네트워크 최대8초·한 추출30초·응답12MB·적재2만건 상한을 둔다.

## 확인 결과

- **원본/제한 조회 정합성: 36/36조건 통과.** 반환 거래의 값·시간·노드·방향과 기준 조회가 일치했다.
- **생략 발생: 9/36조건.** 현재 자료에서는 계좌별50건 상한으로 생략됐고 전체1,000건 상한에는 도달하지 않았다.
- 대표 사례는2홉에서64/115건, 3홉에서64/118건만 포함됐다. 홉을 늘리는 것만으로 계좌별 상한에 막힌 연결이 복구되는 것은 아니다.
- 확인한36조건에서는 제한 때문에 사라진 **룰 종류가 없었다.** 다른 자료의 미탐지나 일반 탐지 성능을 보장하지 않는다.
- 인덱스6개는 ONLINE이었다. 대상 조회는 `DirectedRelationshipIndexSeek`, 확인한 계좌 조회5개는 `NodeUniqueIndexSeek`를 사용했고 `AllNodesScan`은 없었다. 시간 인덱스가 모든 조회에서 사용됐다는 뜻은 아니다.
- 현재 기본 데이터 검사 **31개 통과**(기존16+신규15). 기존 룰·RAG·공통 추출·고정 평가 코드는 변경하지 않았다. 거래 데이터 쓰기·실제 LLM 호출은0회다.

첫 관측과 최종 코드 확인 결과는 각각 `artifacts/db-query-audit-20261117.json/.md`, `artifacts/db-query-audit-20261117-v2.json/.md`에 별도로 보존한다. JSON에 샘플·코드 해시·자료 지문·실행 계획을 기록하며, 기존 파일을 덮어쓰지 않는다.

## 해석과 다음 연결

**거래 포함 비율은 AML Recall이 아니다.** 분모는 이미 적재한 합성 시연 자료 안에서 같은 시간/홉으로 도달할 수 있는 거래다. 전체 IBM 데이터나 은행 원장의 범위를 대표하지 않는다. 샘플 간 지연은 서로 다른 범위가 섞인 값이고, 한 PC의 관측을 대규모 동시 부하·콜드 캐시·운영 SLA·RAG/모델/UI 지연으로 일반화하지 않는다.

현재 `truncated=true`와 부분 조회 안내는 유지한다. 전역 상한을 일괄 확대하기 전에 다음을 백엔드/프론트와 합의한다.

1. **선택 계좌만 추가 조회:** 시각·거래 ID 정렬을 고정한 페이지 기준, 최대 반환/요청 횟수·시간 예산, 중복 제거를 정의한다.
2. **보고서 입력 고정:** 추가 조회로 그래프가 바뀌면 기존 Context/초안을 그대로 사용하지 않고 새 입력으로 재검사한다.
3. **생략 안내:** 일부 연결 거래를 보지 못했다는 사실과 정상 확정 불가를 유지하고, 적재 범위 밖의 개수는 추정하지 않는다.
4. **운영 성능:** Spring/공식 드라이버 연결 후 큰 계좌와 동시 요청에서 다시 측정한다.

PROFILE은 실제 조회를 실행한 결과/계획을 반환한다. 현재 관리자용 HTTP 경로는 Neo4j5.26에서 deprecated이며 운영 연결은 기존 Spring 접근 원칙을 따른다. [Neo4j 공식 안내](https://neo4j.com/docs/http-api/current/profile-query/)
