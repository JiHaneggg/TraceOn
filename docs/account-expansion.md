# 선택 계좌의 제한된 추가 조회 — 2026-11-18

## 화면에서 사용하는 방법

1. 거래와 기간·홉을 선택한다. 최초 조회의 계좌당 최근 50건 기준은 유지한다.
2. 그래프 아래 **생략된 계좌 거래 더 확인하기**에서 계좌를 선택하고 **최대 25건 더 조회**를 누른다. 추가 조회 가능한 계좌는 선택 상세에서도 같은 버튼을 제공한다.
3. 새 거래를 기존 그래프에 합쳐 `주변 연결`로 표시하고 계좌/거래 수·룰 점수·근거를 다시 계산한다. 이번에 추가된 송금선은 파란 점선이며, 대상·룰 근거 색상은 우선 유지한다.
4. 기존 RAG 초안은 지운다. **근거·초안 준비**로 갱신된 전체 조회 그래프에 대한 초안을 새로 검증한다.

기간·홉 변경이나 새로 조회는 별도의 분석을 시작한다. 계좌 목록은 현재 알려진 그래프에서 대상 거래 양 끝점으로부터 홉 상한보다 가까운 계좌만 포함한다. 새 거래로 도달 가능해진 계좌도 해당 범위 안에서만 수동 조회할 수 있다. 자동으로 모든 연결을 순회하지 않는다.

## API 계약

기존 GET `/api/graph`의 공통 `graph`, `ruleResult` 규격은 유지하며, 최상위 `accountExpansion`과 임시 `reviewSnapshotId`를 사용한다.

```json
POST /api/graph/expand
{"snapshotId":"<현재 reviewSnapshotId>","accountKey":"<응답 후보 계좌 키>"}
```

응답은 GET graph와 같은 구조이며 새 `reviewSnapshotId`를 반환한다. 클라이언트가 보낸 커서·기간·홉·건수·그래프·Cypher는 허용하지 않는다. 선택 계좌가 현재 후보인지 서버에서 검증한다. 같은 Origin, JSON, 2KB, 명시적 두 필드만 허용한다.

| 항목 | 기준 |
|---|---|
| 추가 조회 한 번 | 다음 원본 행 최대 25건 + 다음 페이지 존재 확인 1건 |
| 분석당 추가 조회 | 최대 8회 |
| 계좌당 추가 조회 | 최대 4회 |
| 합친 그래프 | 중복 없는 거래 최대 1,000건 |
| 시간·경로 범위 | 최초 대상 거래, asOf, windowStart, hops 고정 |
| DB 요청 | 기존 동시 조회 2개·요청 내 20초 예산·개별 HTTP 대기 최대 8초 유지 |
| DB 응답 크기 | 고정 읽기 한 번당 최대 4MB |
| 임시 상태 | 최대 24개·20분, 재시작/퇴출/만료 시 재조회 |

`accountExpansion`에는 `enabled`, `canExpand`, `pageSize`, `pagesUsed`, `maxPages`, `maxAccountPages`, `maxTotalEdges`, `budgetReached`, `initialTransactionCount`, `totalAddedTransactions`, `candidates`, `lastPage`를 제공한다. 후보의 `reason`은 `more_history`(초기 50건 뒤에 이력 있음) 또는 `unqueried`(이번에 새로 도달한 계좌)다. `canExpand=false`인 후보는 계좌별 상한에 도달했음을 뜻한다.

`lastPage`의 `readRows`, `addedTransactions`, `duplicateTransactions`, `addedTxIds`로 원본 확인 행 수와 실제 추가 거래 수를 구분한다. 다른 계좌에서 이미 읽은 거래가 포함될 수 있어 25행 조회가 항상 새 거래 25건을 뜻하지 않는다. 중복만 읽어도 커서는 전진하고 조회 예산은 소모한다. 전체 1,000건까지 남은 자리가 25개 미만이면 페이지 크기도 줄여 합치지 못한 거래를 건너뛰지 않는다.

## 원본·초안 보호

- 서버에 보관한 커서 `(timestamp DESC, txId DESC)`로 다음 행을 읽는다. 동시각 거래도 ID로 구분하고 기존 ID·방향·금액/통화 문자열을 유지한다. 신규 행의 시간창·계좌 연결·정렬·중복 여부를 검사한다.
- 관리형 시연 자료의 `TraceOnDataset` 이름/SHA-256을 최초 조회와 매 추가 조회 앞뒤에 확인한다. 매 페이지에서 기존 그래프의 모든 거래(최대 1,000건)가 원본과 같은지도 대조한다. 버전/기존 값이 바뀌면 409로 중단하고 기존 초안의 후속 조회·재검사·다운로드를 차단한다.
- 이 보호는 **조사 중 변경하지 않는 관리형 시연 DB**가 전제다. 관리 마커를 갱신하지 않은 외부 쓰기나 뒤늦게 삽입된 과거 거래 전체를 감지하는 트랜잭션 스냅샷 기능은 아니다. 운영에서는 Spring의 버전 관리/일관된 조회 설계가 추가로 필요하다.
- 추가 조회가 성공하면 이전 그래프 스냅샷을 폐기한다. 해당 스냅샷의 초안은 409로 거부한다. 준비/사실/인용/재검사 중 그래프가 무효화돼도 반환 직전에 다시 확인한다. UI의 거래/기간/홉 전환은 대기 중 응답을 무시한다.
- 같은 부모 스냅샷·계좌의 재전송은 아직 최신인 성공 결과를 그대로 반환하며 예산을 중복 차감하지 않는다. 더 진행된 부모나 다른 계좌 재전송은 409, 같은 스냅샷 동시 조회는 429다. 네트워크 실패 시 그래프·커서·예산은 바꾸지 않는다.
- `graph.meta.queryMode=bounded_account_pages_v1`, `additionalReadPages`, `additionalPageSize`로 추가 조회 상태를 남긴다. 미확인 후보/조회 상한이 남으면 `truncated=true`를 유지한다. `sourceGraphComplete=false`는 언제나 유지한다. 현재 범위에서 후보가 없어도 전체 원장/잔액/실소유자를 확인한 것은 아니다.
