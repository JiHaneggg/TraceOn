# 팀장·DB 담당 작업 현황 — 2026-11-14

## 최종 사용자 흐름

**의심거래 선택 → 연결 계좌·송금 경로 표시 → 의심 경로 강조 → 룰 점수와 판단 근거 확인 → 보고서 확인**

이 흐름이 실제 Neo4j 조회 결과로 화면에서 이어지는 것이 MVP의 완료 기준이다. 현재는 데이터·DB·룰 평가 기반까지 구현했으며, 사용자 화면을 포함한 전체 흐름은 아직 완성하지 않았다.

| 흐름 | 준비된 것 | 남은 구현 |
|---|---|---|
| 의심거래 선택 | 고정 거래 ID와 시연용 대상 목록 | 거래 목록·필터·선택 UI, Spring 목록 API |
| 연결 계좌·송금 경로 표시 | Neo4j의 계좌·송금 모델, 제한된 조회, 공통 그래프 JSON | Spring Graph API와 실제 Neo4j 연결, Cytoscape.js 등으로 그래프 렌더링 |
| 의심 경로 강조 | 룰 결과의 `evidenceTxIds`와 `ruleId` | 거래 ID를 화면의 선과 연결해 색상·강조 표시, 노드·선 클릭 상세정보 |
| 룰 점수·근거 확인 | 룰 API, 시간·건수·상대 계좌 수·통화별 금액 집계 | 화면 표시, ML 점수 정규화·결합, 조사의 제한 범위 표시 |
| 보고서 확인 | 거래 ID·계산된 사실·검증 결과 JSON | LLM 근거 설명·STR 초안 생성, 사실/해석 검증, 저장·화면·다운로드 |

## DB·룰 담당으로 완료한 작업

- IBM HI-Small 거래·계좌·패턴 원본을 다운로드하고 전처리했다. 거래 5,078,345건, 계좌 515,088개이며 계좌 정보 누락은 0건이다.
- 계좌 키는 은행 ID와 계좌번호를 함께 사용하고, 원천 행 기준의 고정 `txId`를 부여했다.
- Neo4j 그래프 모델은 `(:Account)-[:TRANSFER]->(:Account)`다. 인덱스·제약조건과 원본 금액 문자열 보존을 구현했다.
- 실제 Neo4j에는 시연용 거래 1,902건·계좌 597개를 적재했다. 12개 사례의 조회 결과와 원본을 대조했다.
- 대상 거래 이전 7일, 기본 2홉, 계좌별 최근 50거래, 최대 1,000거래로 조회를 제한한다. 정답 라벨을 룰 입력에서 제외했다.
- 집금·분산·시간 순서를 확인하는 순환 룰과 로컬 HTTP API를 구현했다. 점수는 확률이 아닌 휴리스틱이다.
- 새 검증 250건·최종평가 250건을 구성하고 216개 조건을 비교했다. 기존 결과와 새로운 고정 설정·평가 결과를 보존했다.
- V2에서는 세탁 표본 100건 중 88건을 찾았지만 정상 150건 중 99건을 오탐했다. 원본 분포 보정 Recall은 87.42%, 오탐률은 66%다. 후보는 연구용으로 남겼다.
- 전처리·평가·API 등 자동 테스트 40개를 통과했다.

## 지금 남은 DB 담당 작업 — 우선순위

1. **500건 평가도 Neo4j 조회 경로로 연결한다.** 현재 500건 평가는 오프라인 SQLite 인덱스에서 그래프 JSON을 추출했다. SQLite는 평가 준비용이며 운영 DB를 대체하지 않는다. 시연용 1,902건만 적재된 현재 DB와 대규모 평가 범위를 구분해야 한다. 기존 500건은 조회 결과 일치 검증에 사용할 수 있지만 룰 고도화의 새로운 최종평가로 재사용하지 않는다.
2. **백엔드 담당과 Graph API를 연결한다.** DB 담당은 스키마·안전한 Cypher·시각/금액/ID 규격·조회 제한을 제공하고, Spring 백엔드는 API와 운영 조회를 담당한다. 조회 시점과 대상 거래 시점의 의미도 고정한다.
3. **시각화용 응답을 프론트 담당과 합의한다.** 계좌 노드 ID, 거래 선 ID, 송금 방향, 금액·통화·시각, 대상 거래 여부, 의심 근거 ID를 공통 JSON에 연결한다. DB 담당은 실제 경로와 근거 ID가 일치하는지 검증한다. 화면 제작은 프론트 담당과 협업한다.
4. **허브 계좌·성능·정확성을 확인한다.** 큰 그래프에서 쿼리 실행계획과 지연시간, 시간 창·홉·반환 제한에 의한 누락을 측정한다. 원본 거래 수·중복·금액·시각 대조를 유지한다.
5. **룰의 오탐을 줄이고 ML 결합을 준비한다.** 룰 점수·계산된 특성·근거 ID를 ML/백엔드 담당에게 제공한다. 더 높은 Recall만으로 후보를 채택하지 않고 정상 알림 수와 처리 비용을 함께 확인한다. 다음 성능 변경은 새 최종평가를 확보한다.
6. **보고서 저장·추적 규격을 합의한다.** 분석 실행 ID, 룰/모델 버전, 근거 거래 ID, 판단 시각, 사람 검토 상태와 보고서 저장 방식을 백엔드·LLM 담당과 정한다.

## 팀장으로 관리할 작업

- 위 5단계 흐름을 전체 MVP 범위로 유지한다. DB·룰 모듈 완성과 화면을 포함한 E2E 완성을 구분한다.
- UI·백엔드·ML·LLM 담당자와 API 입출력, 근거 ID, 주차별 데모를 맞춘다.
- 의심 경로의 실제 조회와 강조 표시를 먼저 연결하고, 점수·근거 화면, ML 결합, 보고서 순서로 통합한다.
- 골든 케이스 시연과 통계적 성능 평가를 구분하고, 전 과정을 회의록·설계 결정에 남긴다.
